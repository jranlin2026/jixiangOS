# 业务订单部分导入设计

## 背景

订单和售后挽回订单共用批量导入流程。当前服务端预检已经能把文件拆分为“可导入、警告、被阻止”三类，但只要存在一条被阻止记录：

- 前端就禁用确认按钮；
- 服务端确认接口也拒绝创建整个后台任务。

这导致一份文件中大部分合法记录无法先行导入。例如 59 条记录中有 51 条可导入、8 条被阻止时，当前只能修正全部 8 条后重新上传。

## 目标

订单和售后挽回订单统一支持：

- 自动跳过预检被阻止的记录；
- 一次性后台导入所有可导入和警告记录；
- 保留被阻止记录的原因、错误报告和完整批次审计；
- 不削弱预检签名、防篡改、附件归属、重复订单号预留和一次性确认机制。

## 非目标

- 不允许强制导入被阻止记录。
- 不增加逐行手动勾选。
- 不改变单行校验规则以及 `ready`、`warning`、`blocked` 的业务含义。
- 不把预检时可导入、确认时已经不再满足条件的记录静默跳过。
- 不改变后台执行阶段现有的逐行失败隔离规则。

## 方案比较

### 方案一：仅前端过滤

前端只把非阻止记录提交给现有确认接口。

优点是改动小。缺点是服务端无法权威确认过滤集合，且提交内容与整份文件的预检哈希不一致，容易破坏防篡改和审计链路。因此不采用。

### 方案二：服务端权威过滤（采用）

前端仍提交完整文件和一次性预检凭证，并明确请求“仅导入符合条件的记录”。服务端重新校验完整文件，核对预检快照，再由服务端筛选非阻止记录创建任务。

该方案同时保留安全边界、完整批次口径和一键操作体验。

### 方案三：生成净化文件后重新上传

系统生成只包含可导入记录的新文件，由用户重新上传预检。安全边界清晰，但增加重复下载、上传和预检步骤，不符合一键导入目标。因此不采用。

## 交互设计

### 预检结果

继续展示全部原始记录及统一分页，统计口径保持：

- `totalCount`：原文件总记录数；
- `readyCount`：可以进入后台任务的记录数，包含 `ready` 和 `warning`；
- `warningCount`：允许导入但需要提示的记录数；
- `blockedCount`：不会进入后台任务的记录数。

有被阻止记录时，提示文案调整为：

> 预检完成：可导入 51 条，警告 0 条，被阻止 8 条。确认后将跳过被阻止记录，仅导入可导入记录。

### 确认按钮

- `readyCount > 0` 时允许点击，不再因 `blockedCount > 0` 禁用。
- 有被阻止记录时显示：`跳过 8 条并后台导入 51 条`。
- 没有被阻止记录时保持：`确认并后台导入 59 条`。
- `readyCount === 0` 时继续禁用，提示“没有可导入的数据”。

### 错误报告

被阻止记录继续出现在预检表格和错误报告中。用户可以修正这些记录后作为新文件重新导入。

任务创建后，预检被阻止记录不计入后台任务失败数；后台任务失败数只表示已经进入任务但执行失败的记录。

## 接口与安全契约

确认请求增加显式模式字段，例如：

```ts
mode: 'eligible_only'
```

前端仍提交完整记录集合、确认凭证和原文件名。服务端按以下顺序处理：

1. 校验用户权限、文件名、凭证签名、操作者、模块和有效期。
2. 规范化完整请求记录并校验完整文件哈希，防止预检后修改文件内容。
3. 重新加载当前业务目录并重新校验全部记录。
4. 从持久化预检批次读取原预检行状态，核对每个行号及其可导入资格。
5. 如果原先可导入的集合与当前重新校验后的可导入集合不一致，返回 `409`，要求重新预检。
6. 由服务端筛选 `ready` 和 `warning` 记录。
7. 仅针对筛选后的记录校验附件归属与完整性。
8. 在一次数据库事务中消费预检凭证、预留筛选后记录的业务编号并创建后台任务。

客户端传入的模式只表达用户选择，不能直接决定哪些行被导入。最终集合必须由服务端根据已签名、已持久化且重新校验的预检结果确定。

## 附件处理

对于 ZIP 导入包：

- 前端根据服务端预检结果，只上传可导入和警告行引用的附件；
- 被阻止行引用的附件不上传；
- 确认请求仍携带完整原始行，以维持整份文件哈希；
- 服务端先用不含上传结果的原始业务字段核对文件哈希，再仅校验可导入行的附件 ID、所有权、分类、文件名和预检草稿标识；
- 确认失败且可确定任务未创建时，前端继续清理本次上传的附件。

附件 ID 是确认阶段产生的传输字段，不应改变预检时对原文件业务内容计算的哈希。

## 持久化与审计

`BusinessImportBatch` 保留原文件统计：

- `totalCount`：原文件总数；
- `readyCount`：预检可提交数；
- `warningCount`：预检警告数；
- `blockedCount`：预检阻止数；
- `rows`：完整预检结果，包括被阻止原因。

`BusinessImportJob` 和 `BusinessImportJobItem` 只保存实际提交的 `ready`、`warning` 记录：

- `job.totalCount === batch.readyCount`；
- 初始 `failedCount === 0`；
- 不为预检阻止记录创建失败任务项；
- 业务编号只为实际提交记录预留。

批次详情因此可以同时回答“原文件有多少条、预检挡住多少条、实际提交多少条、后台成功或失败多少条”。

## 并发与一致性

- 确认凭证继续只能消费一次。
- 确认事务继续对预检批次加锁。
- 实际提交记录的第三方订单号继续使用唯一预留表，防止并发重复导入。
- 预检后配置、客户匹配、订单号占用或权限导致可导入集合变化时，整次确认返回 `409` 并要求重新预检。
- 后台执行期间发生的单行变化仍按现有机制记录为任务行失败，不回滚其他已成功行。

## 兼容性

- 订单和售后挽回订单采用相同部分导入规则。
- 没有阻止项的现有导入行为与接口结果不变。
- 旧客户端未提交 `eligible_only` 时保持现有全量安全行为，避免接口升级期间意外改变语义。

## 验证计划

### 服务层

- 混合文件能够创建只包含 `ready` 和 `warning` 行的任务。
- 全部被阻止时拒绝创建任务。
- 原文件哈希变化时拒绝确认。
- 预检后可导入集合变化时返回 `409`。
- 凭证重复消费、过期、换用户或换模块继续被拒绝。
- 只校验并保存符合条件行的附件。

### 持久化层

- 批次保留完整统计和所有行结果。
- 任务及任务项只包含实际提交行。
- 初始失败数为零。
- 只预留实际提交行的第三方订单号。
- 并发确认只能成功一次。

### 前端

- 有阻止项但存在可导入项时按钮可用。
- 按钮和提示明确展示导入数与跳过数。
- 全部被阻止时按钮禁用。
- 错误报告仍包含被阻止行。
- ZIP 包只上传符合条件行引用的附件。
- 订单和售后挽回订单两个入口行为一致。

### 回归

- 无阻止项的普通 Excel 和 ZIP 导入。
- 警告行导入。
- 后台任务轮询、恢复、部分执行失败和错误报告。
- 导入后的审核导航与批次查询。

## 验收标准

以 59 条记录、51 条可导入、8 条被阻止为例：

1. 页面允许点击“跳过 8 条并后台导入 51 条”。
2. 后台任务只创建 51 个任务项，初始失败数为 0。
3. 8 条被阻止记录不会写入订单或售后挽回订单，也不会占用业务编号。
4. 批次仍显示原文件 59 条、可提交 51 条、阻止 8 条。
5. 错误报告能够下载这 8 条记录及原因。
6. 如果确认前资格发生变化，系统不静默导入不同数量，而是要求重新预检。
