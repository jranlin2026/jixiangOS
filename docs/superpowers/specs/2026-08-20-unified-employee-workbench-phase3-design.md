# 极享OS统一员工工作台第三阶段设计

日期：2026-08-20
状态：待产品确认后进入实施计划

## 1. 背景

极享OS已经完成侧边栏分类，以及内容运营、发布计划、员工任务、执行模板和经营驾驶舱之间的基础串联。现状能够验证单条业务链路，但仍然存在以下问题：

- 员工需要进入不同业务模块寻找待处理事项；
- 首页聚合了多种待办，但不同待办仍使用不同状态、操作和统计口径；
- 岗位固定任务需要管理员手工点击生成；
- 到期、逾期、退回和确认缺少统一提醒；
- 主管只能看到部分任务台账，不能统一管理团队负荷和流程阻塞；
- 老板能看到局部进度，但不能按部门、员工、业务来源下钻；
- 内容素材、发布执行和效果数据尚未形成结构化复盘闭环。

第三阶段的目标不是继续增加孤立页面，而是把极享OS升级为员工统一执行入口、主管统一协同入口和老板统一经营反馈入口。

## 2. 产品目标

完成后必须实现：

> 员工打开极享OS首页，就能知道今天需要完成什么，并在系统中提交结果；主管能够管理团队异常、负荷与确认；老板能够看到公司各业务流程由谁负责、进展如何、哪里阻塞以及产生了什么结果。

### 2.1 成功标准

1. 进入系统的业务事项都有唯一负责人、来源、截止时间和可回溯业务记录。
2. 员工无需逐个打开业务模块寻找任务，首页能够覆盖本人所有可执行事项。
3. 主管能够完成确认、退回、转派、催办和异常处理。
4. 固定岗位任务按上海业务日期自动生成，重复运行不会产生重复任务。
5. 状态变化能够生成站内通知；通知失败不能回滚已提交的业务事务。
6. 老板统计能够按公司、部门、员工、任务来源和时间范围下钻。
7. 营销内容能够从素材、审核、派发、发布证据一直追踪到效果数据。
8. 旧任务、旧发布计划、旧URL和既有权限继续可用。

## 3. 产品边界

### 3.1 本阶段包含

- 统一工作事项模型与状态机；
- 岗位任务自动生成与补偿；
- 站内通知、到期提醒和逾期提醒；
- CRM、订单、交付、售后、财务、内容运营、商学院和OKR的任务接入；
- 员工工作台、主管团队工作台和老板经营驾驶舱；
- 内容素材结构化存储、发布结果和效果回收；
- 数据迁移、权限、审计和兼容适配。

### 3.2 本阶段不包含

- 自动登录抖音、微信等第三方平台并代替员工发布内容；
- 使用任务统计自动计算工资、提成或绩效处罚；
- 替换各业务模块已有的客户、订单、交付和财务状态机；
- 第一版直接接入企业微信、短信等外部通知渠道；
- 在当前服务器存储视频文件，视频继续保存受控的外部链接。

## 4. 核心原则

### 4.1 业务数据归原模块，执行责任归工作台

客户、订单、交付、售后和财务数据继续由原模块管理。工作台只保存执行所需的责任、时限、状态、证据和来源引用，不复制完整业务对象。

### 4.2 扩展现有 EmployeeTask，不建立第二套任务系统

现有 `EmployeeTask` 已具备负责人、日期、证据、确认和来源字段。第三阶段在此基础上扩展，不新建并行的 `WorkItem` 主表，避免历史任务迁移和双写问题。

### 4.3 直接创建加定时对账

业务命令成功后直接创建或更新任务，保证员工及时看到事项；后台对账任务定期扫描需要接入的业务状态，补偿通知失败、服务重启或历史数据造成的遗漏。两条路径使用同一个幂等键。

### 4.4 工作台不越权

任务可见性不能扩大原业务模块的数据权限。用户可以看到任务摘要，但进入业务详情时仍由原模块再次鉴权。主管统计只覆盖其部门树；公司级经营统计仅对相应驾驶舱权限开放。

## 5. 用户与角色

### 5.1 员工

- 查看本人今天、逾期、退回、即将到期和协同事项；
- 领取可领取任务、开始处理、提交结果和证据；
- 打开来源业务记录；
- 查看自己的历史执行记录与退回原因。

### 5.2 主管

- 查看授权部门树内的任务；
- 按员工、来源、状态、优先级和日期筛选；
- 确认、退回、转派、催办和取消任务；
- 查看团队负荷、逾期和长期未处理事项；
- 查看任务完整操作时间线。

### 5.3 业务管理员

- 配置岗位执行模板；
- 查看任务生成和业务接入异常；
- 手工补生成指定日期的任务；
- 维护内容素材、账号组和发布计划。

### 5.4 老板和经营管理者

- 查看公司级执行数据；
- 下钻部门、员工、来源和具体任务；
- 查看流程阻塞、逾期趋势和内容发布效果；
- 不因驾驶舱权限自动获得业务记录编辑权限。

## 6. 统一任务模型

### 6.1 EmployeeTask新增字段

在保留现有字段的基础上增加：

- `taskType`：`ACTION`、`APPROVAL`、`CONFIRMATION`、`FOLLOW_UP`、`LEARNING`、`PUBLISH`；
- `priority`：`LOW`、`NORMAL`、`HIGH`、`URGENT`；
- `businessModule`：标准模块代码；
- `sourceRoute`：前端可导航的站内相对路径；
- `sourceLabel`：员工可理解的来源说明；
- `status` 扩展为：`PENDING`、`IN_PROGRESS`、`COMPLETED`、`CONFIRMED`、`RETURNED`、`CANCELED`；
- `startedAt`、`canceledAt`、`canceledById`、`canceledReason`；
- `collaboratorIds`：协作人ID数组；
- `estimatedMinutes`：预计工作量；
- `qualityScore`、`qualityComment`：主管确认时的可选质量记录；
- `remindedAt`、`lastOverdueNotifiedAt`：通知节流；
- `sourceVersion`：来源业务版本或更新时间，用于对账；
- `sourceKey`：全局唯一幂等键。

### 6.2 唯一性

新增唯一索引 `sourceKey`。格式由来源适配器生成，例如：

- `customer_todo:{todoId}`
- `order_review:{orderId}:{reviewStage}`
- `delivery_step:{deliveryId}:{stepId}`
- `marketing_publish:{planId}:{accountId}`
- `academy_task:{academyTaskId}`
- `okr_task:{okrId}:{krId}:{period}`
- `template:{templateId}:{employeeId}:{workDate}`

旧任务回填稳定的 `sourceKey`；无法可靠推导的历史记录使用 `legacy:employee_task:{id}`。

### 6.3 状态机

- `PENDING → IN_PROGRESS`：员工开始处理；
- `PENDING/IN_PROGRESS/RETURNED → COMPLETED`：员工提交结果；
- `COMPLETED → CONFIRMED`：主管确认；
- `COMPLETED → RETURNED`：主管退回并填写原因；
- `PENDING/IN_PROGRESS/RETURNED → CANCELED`：授权人员取消；
- `RETURNED → IN_PROGRESS`：员工重新处理；
- `CONFIRMED/CANCELED` 为终态，只有具备任务治理权限的管理员可重开。

每次状态变化必须写入独立的任务活动记录，不能只依赖任务主表上的最终字段。

## 7. 任务活动、证据与协同

### 7.1 TaskActivity

记录：

- 状态变化；
- 创建、开始、提交、确认、退回、转派、催办、取消和重开；
- 操作人、操作时间、变更前后值；
- 评论、退回原因和转派原因；
- 业务来源同步事件。

### 7.2 证据

继续使用 `TaskEvidence`，支持：

- 文本；
- 发布链接；
- 截图链接；
- 图片附件引用；
- 业务记录引用。

证据必须进行协议、长度和权限校验。营销发布至少提交发布链接或截图链接之一。

### 7.3 转派

转派时：

- 校验新负责人处于主管授权部门树；
- 保存原负责人和新负责人；
- 生成任务活动；
- 通知双方；
- 不修改原业务记录负责人，除非来源适配器明确支持双向同步。

## 8. 业务来源适配器

### 8.1 接口

每个来源实现统一接口：

```ts
type WorkbenchBusinessModule =
  | 'GENERAL'
  | 'CRM'
  | 'ORDER'
  | 'DELIVERY'
  | 'AFTER_SALES'
  | 'FINANCE'
  | 'MARKETING'
  | 'ACADEMY'
  | 'OKR';

type DesiredEmployeeTask = {
  sourceKey: string;
  taskType: NonNullable<EmployeeTask['taskType']>;
  priority: NonNullable<EmployeeTask['priority']>;
  businessModule: WorkbenchBusinessModule;
  title: string;
  employeeId: string;
  employeeNameSnapshot: string;
  workDate: string;
  sourceVersion?: string | null;
  description?: string | null;
  departmentId?: string | null;
  departmentNameSnapshot?: string | null;
  dueAt?: string | null;
  sourceRoute?: string | null;
  sourceLabel?: string | null;
  collaboratorIds?: string[] | null;
  estimatedMinutes?: number | null;
};

type ReconcileContext = Readonly<{
  now: Date;
  sourceKeys?: string[];
  cursor?: string;
  cursors?: Partial<Record<WorkbenchBusinessModule, string>>;
  limit?: number;
  signal?: AbortSignal;
}>;

type ReconcileError = {
  module: WorkbenchBusinessModule;
  sourceKey?: string;
  message: string;
};

type ReconcileResult = {
  scanned: number;
  created: number;
  updated: number;
  canceled: number;
  unchanged: number;
  failed: number;
  errors: ReconcileError[];
  nextCursors?: Partial<Record<WorkbenchBusinessModule, string>>;
};

type TaskTransitionEvent = {
  taskId: string;
  sourceKey: string;
  businessModule: WorkbenchBusinessModule;
  action: string;
  fromStatus: EmployeeTask['status'];
  toStatus: EmployeeTask['status'];
  actorId: string;
  occurredAt: Date;
};

type WorkbenchSourceAdapter = {
  module: WorkbenchBusinessModule;
  reconcile(input: ReconcileContext): Promise<ReconcileResult>;
  resolveTask(sourceKey: string): Promise<DesiredEmployeeTask | null>;
  onTaskTransition?(event: TaskTransitionEvent): Promise<void>;
};
```

对账的 `limit` 统一收敛到 1–1000 的正安全整数；适配器必须遵守 `signal` 中止。只有传入的 `signal` 已中止时才停止整体对账；单个适配器自身的 `AbortError` 按普通隔离失败处理。对账对外错误统一转换为稳定的模块级安全摘要，不回显适配器错误原文、凭据、连接串或堆栈。聚合结果按适配器输入顺序稳定累加，每个模块的续页位置独立保存在 `nextCursors`，下一轮通过 `cursors` 原样传回；适配器收到 `cursors[adapter.module] ?? cursor`。标量 `cursor` 只用于单适配器及向后兼容，多适配器分页必须使用 `cursors`。同一批次不允许重复模块适配器。单个适配器失败不丢失其他成功结果，但中止信号会立即停止后续适配器。持久化边界可读取历史模块字符串，新适配器只能写入上述标准模块代码。

适配器负责把业务状态转换成“期望任务”，统一同步服务负责创建、更新或关闭任务。

期望任务的 `sourceKey`、`businessModule` 和 `taskType` 仅在创建时确定身份。`syncDesiredTask` 的载荷 `sourceKey` 必须与显式参数完全一致，已存在任务的模块或任务类型也不得被其他来源载荷复用。后续对账只能更新标题、描述、负责人及部门快照、工作日、截止时间、优先级、来源路由与标签、协作人、预计分钟和来源版本；不得覆盖员工结果、证据、生命周期时间或质量字段。

首次同步必须在任务创建的同一事务内写入 `CREATE` 活动；已有任务的来源字段真正变化时，在同一事务内写入一条 `SOURCE_SYNC`，元数据只列变更字段名，不保存字段值。串行化事务保证并发相同更新只写一条 `SOURCE_SYNC`。无变化的重复同步不写活动。原子同步对唯一键冲突 `P2002`、写冲突/死锁 `P2034` 和事务内消失行使用同一套最多三次的有界重试。期望任务消失时仅对 `PENDING`、`IN_PROGRESS`、`RETURNED` 执行既有生命周期的取消迁移；`COMPLETED`、`CONFIRMED`、`CANCELED` 保持不变。

### 8.2 第一批来源映射

#### CRM

- 客户待办进入统一任务；
- 线索长期未跟进形成跟进任务；
- 客户待办完成与任务完成双向同步，使用事务避免一边成功一边失败。

#### 订单

- 待提交补充资料；
- 待审核订单；
- 被退回订单修改；
- 订单完成或取消时关闭未完成关联任务。

#### 交付

- 交付节点负责人任务；
- 节点完成同步任务完成；
- 交付计划延期更新任务截止时间并记录活动。

#### 售后与退款

- 售后处理、挽回、退款审核和退款执行；
- 来源状态终止时取消剩余任务。

#### 财务

- 收款确认、结算审核和付款执行；
- 任务只展示必要摘要，金额详情仍按财务权限读取。

#### 内容运营

- 内容审核；
- 发布计划按账号主要使用人生成发布任务；
- 发布任务确认后写回发布目标状态；
- 效果数据采集生成后续复盘任务。

#### 商学院

- 复用现有课程执行任务；
- 统一进入员工工作台，但课程进度仍由商学院管理。

#### OKR

- KR周期动作和已有任务链接进入工作台；
- 任务完成不自动把KR进度改为100%，只形成可追溯贡献记录。

## 9. 自动调度与补偿

### 9.1 调度服务

新增单实例安全的调度服务：

- 启动时执行当日岗位任务补偿；
- 每个上海工作日凌晨生成岗位任务；
- 每5分钟执行来源对账；
- 每15分钟扫描即将到期和逾期任务；
- 使用数据库租约锁避免多实例重复执行；
- 每次运行写入调度记录，包含开始时间、结束时间、成功数、跳过数和失败摘要。

### 9.2 手工补偿

管理员可以按日期、模块和部门执行补偿。手工补偿调用同一个幂等服务，不提供绕过唯一键的强制重复生成。

### 9.3 故障处理

- 单条来源失败不能阻断其他来源；
- 失败记录进入调度运行明细；
- 连续三次失败生成管理员通知；
- 通知发送失败不回滚任务状态；
- 对账只能修改来源拥有的字段，不能覆盖员工已提交结果。

## 10. 通知设计

复用系统现有 Notification、NotificationDelivery 和 NotificationRule。

### 10.1 通知事件

- 任务创建或转派；
- 截止前提醒；
- 任务逾期；
- 员工提交待主管确认；
- 主管退回；
- 主管确认；
- 任务取消或重开；
- 自动调度连续失败。

### 10.2 去重和节流

- 创建、转派、退回、确认按任务活动ID去重；
- 即将到期每个任务只提醒一次；
- 逾期默认每天最多提醒一次；
- 同一主管的批量逾期事项聚合成一条摘要，避免通知轰炸。

## 11. 员工工作台

### 11.1 页面结构

首页保留“开工指挥条”，工作事项区升级为：

- 今天必须完成；
- 已逾期；
- 被退回；
- 等待我确认；
- 即将到期；
- 我参与的协同事项；
- 已完成记录。

### 11.2 排序

默认优先级：

1. 被退回；
2. 已逾期；
3. 紧急任务；
4. 当日即将到期；
5. 高优先级；
6. 其他任务按截止时间升序。

系统提供排序建议，但不使用不透明的AI评分替代明确规则。

### 11.3 快速执行

任务卡片支持：

- 开始处理；
- 填写结果；
- 上传或填写证据；
- 复制文案和打开素材；
- 打开原业务记录；
- 查看退回原因和任务时间线。

涉及原业务状态修改的复杂操作仍进入业务详情页完成。

## 12. 主管团队工作台

提供桌面表格和移动卡片，二者共享筛选、总数和分页语义。

### 12.1 筛选

- 时间范围；
- 部门和员工；
- 来源模块；
- 状态；
- 优先级；
- 是否逾期；
- 是否需要确认。

### 12.2 操作

- 批量催办；
- 单条确认、退回、转派和取消；
- 查看任务活动和证据；
- 从异常任务进入原业务记录；
- 查看每人待办量和预计工作量。

### 12.3 负荷口径

- 任务数与预计分钟数分别展示；
- 未配置预计分钟数的任务不伪造工作量；
- 工作量只用于发现分配异常，不作为员工绩效结论。

## 13. 老板经营驾驶舱

### 13.1 指标

- 新增任务数；
- 已确认任务数；
- 按时完成率；
- 逾期率；
- 退回率；
- 平均首次处理时长；
- 平均确认时长；
- 当前阻塞任务；
- 按来源、部门和员工分布。

### 13.2 下钻

公司 → 部门 → 员工 → 任务 → 来源业务记录。

驾驶舱统计按公司业务时区计算，日期边界使用 `Asia/Shanghai`。公司级权限可查看全公司聚合；部门权限只查看部门树。

### 13.3 数据解释

- `COMPLETED` 表示员工已提交、待确认；
- `CONFIRMED` 才计入最终完成；
- 按时完成以首次提交时间是否早于截止时间计算；
- 退回后再次提交仍保留首次提交和全部退回次数；
- 被取消任务不进入完成率分母，但单独统计取消量。

## 14. 内容素材与效果闭环

### 14.1 结构化表

新增：

- `MarketingContent`：内容主记录；
- `MarketingContentRevision`：文案和素材版本；
- `MarketingAssetLink`：图片、视频、网盘和外部素材链接；
- `MarketingReviewEvent`：提交、通过、驳回和停用记录；
- `MarketingPublishPlan` 与 `MarketingPublishTarget`：发布计划和账号目标；
- `MarketingPublishResult`：发布链接、截图链接和确认信息；
- `MarketingPerformanceSnapshot`：浏览、互动、咨询和线索数据快照。

### 14.2 迁移

- 从 AppStorage 迁移现有内容、账号组和发布计划；
- 保留旧ID，避免任务来源断链；
- 迁移脚本可重复执行且不覆盖新表中的更新；
- 兼容读取在一个发布周期内保留，写入只进入新表；
- 迁移完成并验证后再单独移除旧写入路径。

### 14.3 效果录入

发布完成后允许录入：

- 实际发布链接；
- 浏览量；
- 点赞、评论、收藏等互动；
- 咨询量；
- 线索量；
- 统计时间。

第一版由员工或运营手工录入，不假定第三方平台开放API。

## 16. 权限与数据范围

沿用现有权限，并增加最小必要动作权限：

- `工作台/本人任务`；
- `工作台/团队任务`；
- `工作台/任务指派`；
- `工作台/任务确认`；
- `工作台/任务治理`；
- `工作台/经营统计`。

旧 `TASK_SELF`、`TASK_TEAM`、`TASK_ASSIGN` 通过兼容映射继续有效。兼容映射不能让旧角色获得公司级数据范围。

## 17. 审计与安全

- 所有写操作保存操作人、时间和来源IP上下文；
- 任务证据不能泄露无权查看的业务详情；
- 驾驶舱只返回聚合或用户有权下钻的数据；
- 转派、取消、重开和批量催办必须写审计记录；
- URL证据只允许 `http` 和 `https`；
- 站内导航只允许系统相对路径，禁止开放重定向；
- 所有列表使用服务端分页。

## 18. 页面与导航

- 侧边栏继续保留“我的工作台”和“经营驾驶舱”固定入口；
- “任务中心”不新增顶级侧边栏，完整历史台账从工作台进入；
- “执行模板”继续归属“企业标准”；
- “内容运营”继续归属“增长运营”；
- 资产管理只管理设备、手机号、账号和交接，不重新承载发布计划。

## 19. 数据迁移与兼容

1. 新增字段全部提供安全默认值或允许为空；
2. 回填历史任务 `sourceKey`、模块和来源标签；
3. 旧任务状态映射到新状态机；
4. 旧发布计划目标关联既有员工任务；
5. 旧URL重定向继续保留；
6. 迁移前后分别生成数量、状态和关联完整性报告；
7. 任何不一致都阻止删除旧数据，不阻止现有业务读取。

## 20. 交付拆分

第三阶段作为一个产品目标，拆成五个连续交付包；每个交付包独立测试、评审和提交，但最终全部完成后才称为第三阶段完成。

### 交付包A：统一任务底座

- 数据模型、迁移、状态机、活动记录、统一服务和兼容API。

### 交付包B：自动化与通知

- 岗位任务自动生成、来源对账、数据库租约锁、提醒和补偿。

### 交付包C：业务来源接入

- CRM、订单、交付、售后、财务、内容运营、商学院和OKR适配器。

### 交付包D：员工与主管工作台

- 员工统一执行、主管协同、移动端卡片、统一分页和任务时间线。

### 交付包E：老板驾驶舱与内容效果

- 公司级统计、下钻、内容结构化迁移、发布效果和复盘。

## 21. 验收场景

### 21.1 员工

Given 员工同时有客户待办、发布任务和交付任务
When 员工进入首页
Then 系统按统一优先级展示三类事项，并且每项都能进入正确业务记录。

### 21.2 自动生成

Given 一个工作日岗位模板和符合岗位的在职员工
When 调度服务在同一天执行两次
Then 每个员工只生成一条任务，第二次记录为跳过重复项。

### 21.3 逾期通知

Given 任务超过截止时间且仍未完成
When 逾期扫描执行
Then 员工收到通知，主管看到异常；同一天重复扫描不重复轰炸。

### 21.4 主管退回

Given 员工提交了需要确认的任务
When 主管填写原因并退回
Then 任务变为被退回，员工收到通知，活动时间线保留提交和退回记录。

### 21.5 来源同步

Given 一个订单审核任务已经生成
When 订单被其他合法入口取消
Then 对账服务取消未完成任务，不删除历史活动。

### 21.6 数据权限

Given 主管只能管理自己的部门树
When 主管查询团队工作台或尝试转派
Then 系统不返回其他部门任务，也拒绝转派给范围外员工。

### 21.7 老板驾驶舱

Given 公司存在已确认、待确认、逾期和被取消任务
When 老板查看指定日期范围
Then 指标使用明确口径，并可下钻到有权查看的任务。

### 21.8 内容效果

Given 已审核内容被派发到多个账号
When 员工提交发布链接并录入效果
Then 内容详情能够按账号展示发布结果和效果快照，且能回溯执行人和任务。

## 22. 测试策略

- 领域测试：状态机、优先级、统计口径和来源幂等键；
- 服务测试：权限、数据范围、对账、转派、通知失败和事务一致性；
- 迁移测试：历史任务和营销内容回填、重复执行和完整性报告；
- API测试：统一接口与旧接口兼容；
- 页面测试：员工执行、主管确认、筛选分页和移动端卡片；
- 调度测试：上海日期边界、多实例租约、重复运行和失败补偿；
- 全量回归：CRM、订单、交付、售后、财务、内容运营、商学院和OKR现有测试必须继续通过。

## 23. 上线策略

1. 数据库迁移先上线，新增字段保持兼容；
2. 统一任务服务以兼容模式运行，旧页面继续可用；
3. 开启岗位自动生成和站内通知；
4. 分模块开启来源适配器并核对数量；
5. 开启员工和主管工作台新界面；
6. 完成内容结构化迁移和驾驶舱统计；
7. 连续运行一个发布周期并核对旧数据后，再移除废弃写入路径。

第三阶段只有在五个交付包全部通过验收、真实角色完成端到端试跑并且数据口径核对一致后，才能标记完成。
